## 看一个例子

一段工作通知，信息被套话埋住了。下面的前后对照是**人工构造的示意**，用于说明编辑方向，不是 Skill 的效果评测。

### 改写前

> 为了进一步加强各部门之间的协同配合、持续提升需求评审工作的效率和质量，我们将对现行会议安排进行优化调整。根据新的安排，从11月1日起，需求评审会将由每周三次调整为每周一次，原则上固定在每周三召开。为确保会议讨论更加聚焦，请各部门务必在周二18:00之前，提前提交需要在会议上决策的相关问题。对于那些在会议上没有得到解决的问题，将由相应的负责人在周五之前对处理进度进行反馈。需要特别说明的是，如遇紧急故障，无需等待例会召开，可以直接联系值班负责人进行处理。

### 改写后

> 11月1日起，需求评审会由每周三次改为每周一次，原则上每周三开。需要决策的问题，各部门须在周二18:00前提交；会上没定下来的事项，由负责人在周五前反馈进度。紧急故障直接联系值班负责人，不用等例会。

变化在于**先说新安排，再说怎么执行**。日期、频率、周三的弹性安排、提交和反馈期限、紧急故障的例外都留着；删掉的是没有增加信息的铺垫和重复说明。如果原文本来就顺畅，不必为了显示“改过”再换一套说法。

## 适合做什么

| 从这里开始 | 对它说 | 它应该怎么处理 |
| :--- | :--- | :--- |
| **有素材，要成文** | “根据这些材料，写一篇给普通读者看的短文，600字以内。” | 组织已有信息；关键事实不足时先确认 |
| **有原稿，要修改** | “把这段改自然些，别改变数字、引语和我的观点。” | 去掉冗余；保留信息和作者语气 |
| **有疑问，要建议** | “这段开头为什么读着生硬？给我两个修改方向。” | 指出具体问题，说明改法 |

它可用于评论、科普、报道、经历、商业文字和访谈。明确要求虚构创作时也能写故事；非虚构任务不会把编出的情节当成事实。

## 快速开始

把整个 [`humanize-zh-writing/`](humanize-zh-writing/) 目录放进使用环境的 skills 目录。以 Codex 默认目录为例：

```bash
git clone https://github.com/shaozhengmao/humanize-zh.git
mkdir -p ~/.codex/skills
cp -R humanize-zh/humanize-zh-writing ~/.codex/skills/
```

入口是 [`SKILL.md`](humanize-zh-writing/SKILL.md)。安装后，直接说清主题、素材、读者、篇幅和必须保留的信息；需要明确调用时，可以在请求中写出 `humanize-zh-writing`。普通写作无需 Python 或 API 密钥。

[`voice.md`](humanize-zh-writing/voice.md) 是可选的风格参考方法，没有绑定某位作者的“声纹”。默认沿用用户或原文的语气；提供样文或主动选择风格时才参考它。

## 使用边界

| 会做 | 不会承诺 |
| :--- | :--- |
| 保留事实、数字、直接引语、信源、否定、条件和作者立场 | 通过 AI 检测器，或判断文章是否由 AI 写成 |
| 缺少真实经历或关键事实时询问、查证，或明确留空 | 用虚构细节填补非虚构材料的空缺 |
| 原文合适时少改或不改 | 每次都大幅改写，或保证比普通提示词效果更好 |

**效果尚未被充分验证。** 现有工具回归和少量写作试用只能检查部分行为，不能证明 Skill 普遍提高了质量。更可靠的做法是用同一模型、同一批真实任务做有无 Skill 的匿名对照，比较事实准确性、作者语气、可读性和返工量。
